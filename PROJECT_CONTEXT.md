# Контекст проекта: Вращающаяся математическая головоломка (мультиплеер)

## Цель проекта (уточнено)
Это НЕ просто "клик -> поворот фигуры". Реальная концепция:

Головоломка из нескольких равносторонних многогранников (треугольники,
квадраты и т.д.). У соседних фигур есть ОБЩИЕ вершины (точки). В вершинах
стоят числа. При клике фигура физически поворачивается на 1 шаг (как
жёсткое тело — рамка + вершины), и числа в её вершинах циклически
сдвигаются — включая общие вершины с соседними фигурами, что связывает
фигуры между собой.

Есть "линии" — произвольные наборы точек (могут проходить через
несколько фигур сразу), для которых нужно добиться математического
условия (сейчас: сумма = цель). Игрок должен покрутить фигуры так, чтобы
ВСЕ линии одновременно выполняли своё условие — это и есть решение уровня.

Будет НЕСКОЛЬКО уровней (жёстко заданных заранее, не случайная генерация).
Ещё не решено: показывать все уровни на одном экране или отдельный экран
выбора уровня — решим на этапе фронтенда, на бэкенд-архитектуру не влияет.

Мультиплеер: любой подключённый игрок может крутить любую фигуру в любой
момент — совместное решение ОДНОЙ головоломки, все видят изменения в
реальном времени (через WebSocket, синхронизация состояния сервером).
Уже реализовано на фронтенд-прототипе: пока крутится одна фигура, клик по
другой (или по той же) игнорируется до конца анимации (глобальный флаг
isAnimating) — предвосхищает будущую многопользовательскую блокировку.

Это НЕ приложение внутри Miro — отдельный самостоятельный веб-сервис.

## Архитектура (согласовано)
```
Браузер (клиент) <--WebSocket--> Python-сервер (FastAPI) <--WebSocket--> Браузер (клиент)
```
Сервер хранит состояние (текущие значения точек) как единый источник
правды. Клик по фигуре в браузере -> сообщение по WebSocket серверу ->
сервер поворачивает фигуру в PuzzleState -> рассылает всем подключённым
клиентам новое состояние -> все видят синхронно.

ТЕКУЩИЙ СТАТУС: прототип интерфейса (app/static/index.html) пока работает
ПОЛНОСТЬЮ АВТОНОМНО на чистом JS, без связи с бэкендом (дублирует логику
rotate/сумм на клиенте вручную). WebSocket-подключение к реальному
PuzzleState с бэкенда — ещё предстоит сделать (см. план).

## Модель данных головоломки (бэкенд, реализовано и проверено)
Ключевая идея: точки существуют независимо от фигур. Фигуры и линии — это
просто СПИСКИ id точек, ссылающиеся на общий пул. Общие вершины между
фигурами получаются естественно: два Shape ссылаются на один и тот же
point_id.

- **Point** — id + value (число)
- **Shape** — id + point_ids
- **Line** — id + point_ids + operation (пока только "sum") + target
- **Level** — неизменный шаблон: id, name, points, shapes, lines
- **PuzzleState** — состояние КОНКРЕТНОЙ игровой сессии.
  `rotate(shape_id, direction)`, `is_solved()`.

ВАЖНО: backend test-файлы (test_engine_butterfly.py) используют старую
2-точечную версию диагоналей (A-E, B-D, target=6) — фронтенд-прототип
давно ушёл вперёд на 3-точечную версию (A-C-E, B-C-D, target=9). Нужно
синхронизировать при подключении реального WebSocket.

## Фронтенд-прототип (app/static/index.html) — АРХИТЕКТУРА АНИМАЦИИ
Это была самая сложная часть проекта — потребовалось несколько итераций,
чтобы прийти к надёжному решению. Финальная архитектура:

### Геометрия
Два равносторонних треугольника-бабочка, ГОРИЗОНТАЛЬНО (лежат на боку):
  A(120,150), D(120,330) — база левого треугольника (вершина смотрит вправо)
  B(432,150), E(432,330) — база правого треугольника (вершина смотрит влево)
  C(276,240) — общая вершина, ровно на пересечении обеих диагоналей
Центроиды (для поворота): left=(172,240), right=(380,240)

### КЛЮЧЕВОЙ АРХИТЕКТУРНЫЙ УРОК: текст должен быть НЕЗАВИСИМ от рамки
Изначально пробовали класть <text> ВНУТРЬ вращающейся SVG-группы (рамка +
кружки), с "противо-вращением" текста, чтобы цифры оставались читаемыми.
Это привело к тонкому, долго не находившемуся багу: элемент "text-left-A"
физически ПЕРЕМЕЩАЛСЯ вместе с родительской группой при повороте (т.к.
лежал внутри неё), поэтому когда мы писали в него values.A, оказывалось,
что на экране это значение появляется НЕ на месте A, а там, куда его
унёс поворот родителя — путаница между "именем" элемента и его реальным
положением на экране. Итоговое РЕШЕНИЕ: текст полностью ВЫНЕСЕН из
вращающихся групп, это независимые <text id="text-A">...</text> и т.д.
прямо в SVG, всего 5 штук (по одной на точку A/B/C/D/E — БЕЗ дублирования
для общей C, т.к. текст больше не привязан к конкретной фигуре). Они
никогда не вращаются и не двигаются — только их textContent обновляется.
Вращаются (физически, как жёсткое тело) ТОЛЬКО рамки: линии-рёбра + три
кружка внутри каждой <g class="shape-group">.

### Расчёт направления сдвига чисел — через реальную геометрию, не вручную
Была вторая серия багов из-за попыток вручную угадать порядок точек
(по/против часовой стрелки) для формулы циклического сдвига — несколько
раз ошиблись с направлением. ИТОГОВОЕ РЕШЕНИЕ: функция rotatePoint(x, y,
cx, cy, angleDeg) — стандартная формула поворота точки (та же математика,
что и CSS transform rotate()). В applyDataRotation для каждой вершины
ВЫЧИСЛЯЕТСЯ, где она физически окажется после поворота, и находится
ближайшая среди вершин ЭТОЙ ЖЕ фигуры — туда и "переезжает" число. Это
исключает ручное угадывание направления — теперь оно математически
гарантированно совпадает с тем, что видно на экране.
Подтверждённые (вычисленные) циклы при клике (direction=+1, по часовой):
  левый треугольник: A → C → D → A
  правый треугольник: B → E → C → B

### Вращение как "жёсткое тело" (рамка + кружки) — без сброса угла
`rotationState.left` / `.right` НАКАПЛИВАЮТСЯ бесконечно (никогда не
сбрасываются к 0) — на каждый клик += ±120°. Это принципиально важно:
раньше пробовали "мгновенно сбрасывать" накопленный угол обратно к 0
после каждого поворота (чтобы не расти бесконечно), но это ломало
цветовую/пространственную картину — ведь кружки реально физически едут
на новое место при повороте, и сброс обнулял бы этот эффект.
Поворот строится функцией rotationAroundPoint(px, py, angleDeg) —
явная схема `translate(px,py) rotate(angleDeg) translate(-px,-py)`,
НЕ через CSS `transform-origin` (тот способ давал баги/непредсказуемое
поведение при вложенных повёрнутых группах — отказались от него).
При загрузке страницы группы rotate-фигур ИНИЦИАЛИЗИРУЮТСЯ этой же
составной формулой на угол 0 — иначе самый первый клик анимируется
браузером через матричное разложение по-другому (визуально "странно"),
чем все последующие клики.

### Анимация клика — три последовательных этапа (setTimeout-цепочка)
1. Цифры этой фигуры ПЛАВНО гаснут (opacity 0, 0.25с) — безопасно
   гасить плавно, т.к. текст больше не связан с рамкой физически.
2. После угасания — рамка (линии+кружки) физически поворачивается на
   120° (1.6с, длительность несколько раз увеличивали по просьбе
   пользователя, было изначально 0.4s → 0.9s → 1.6s).
3. После поворота — applyDataRotation() пересчитывает values, render()
   обновляет textContent (цифры всё ещё невидимы), затем цифры плавно
   проявляются обратно (opacity 1, 0.25с).
Итоговая длительность одного клика: 250+1600+250 = 2100мс.
Глобальный флаг `isAnimating` блокирует ЛЮБЫЕ клики (по любой из двух
фигур) на всё время этой последовательности — простой, чем
transitionend-based подход (от которого отказались из-за багов со
всплытием событий от дочерних элементов).
ВАЖНО: длительности FADE_DURATION_MS / ROTATE_DURATION_MS в JS ДОЛЖНЫ
точно совпадать с соответствующими CSS transition — иначе таймеры
разъедутся с реальной анимацией. Явно прокомментировано в коде.

### Визуальный стиль (финальный, после нескольких правок)
- Рамки (линии) и кружки — один тёмно-синий цвет #16213e (было:
  разноцветные кружки lightblue/lightsalmon/plum, убрали по просьбе
  пользователя — "все кружки одного сине-чёрного цвета").
- Толщина линий рамки: 8px (последовательно увеличивали: 2 → 5 → 8).
- Заливка треугольника (кликабельная область, тот же элемент что и
  hit-area для onclick) — того же цвета #16213e = rgb(22,33,62), с
  прозрачностью 0.85 в покое / 0.95 при наведении (почти сплошная;
  по пути перепробовали и полупрозрачные варианты, финально попросили
  сделать сильно непрозрачной).
- Текст цифр — белый (#ffffff), хорошо читается на тёмных кружках.

### Общий пул (диагонали/суммы) — без изменений с прошлой сессии
Таблички "Цель / Сумма" справа, зелёный текст (sum-ok) если совпадает с
целью, иначе тёмный (sum-wrong). Диагонали 3-точечные: A-C-E и B-C-D,
обе target=9.

### Текстуры фона
Папка `app/static/textures/`. Файлы: floor.webp (не идеально бесшовный),
background.jpg (не использован), Tiles_Roughness.jpg (используется,
background-repeat + background-size: 512px 512px на области 853×480px).
ВАЖНЫЙ УРОК (решённый баг): FastAPI не раздавал файлы из static/ без
явного `app.mount("/", StaticFiles(directory="app/static"), name="static")`
в КОНЦЕ main.py (после всех @app.get(...)).
Обсуждали (не сделано): извлечение бесшовных текстур пола из паков
Dungeondraft — свериться с лицензией при публичном релизе.

## Известные технические нюансы (держим в памяти)
- Системный `python`/`py` не работают напрямую — вызываем venv напрямую.
- В PowerShell venv активируется отдельно от cmd.
- Пользователь иногда печатает не в той раскладке клавиатуры (например,
  "знсрфкь" = "pycharm" в ЙЦУКЕН).
- Файлы, добавленные вручную через проводник, часто с пробелами/кириллицей
  в имени — переименовываем в латиницу перед использованием в коде.
- FastAPI НЕ раздаёт файлы из static/ без явного app.mount(StaticFiles).
- При работе с CSS transition + JS setTimeout — длительности ОБЯЗАТЕЛЬНО
  дублировать константой в JS и держать в синхроне с CSS, иначе баги.
- SVG-элементы, вложенные в повёрнутую (CSS transform) группу, физически
  наследуют это перемещение — если что-то должно оставаться на фиксированном
  месте независимо от поворота родителя, его нужно вынести из этой группы,
  а не пытаться компенсировать поворотом на дочернем уровне.
