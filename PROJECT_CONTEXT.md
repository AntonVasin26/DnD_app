# Контекст проекта: Вращающаяся математическая головоломка (мультиплеер)

## Цель проекта (уточнено)
Это НЕ просто "клик -> поворот фигуры". Реальная концепция:

Головоломка из нескольких равносторонних многогранников (треугольники,
квадраты и т.д.). У соседних фигур есть ОБЩИЕ вершины (точки). В вершинах
стоят числа. При клике фигура поворачивается на 1 шаг по кругу (в любую
сторону), и числа в её вершинах циклически сдвигаются — включая общие
вершины с соседними фигурами, что связывает фигуры между собой.

Есть "линии" — произвольные наборы точек (могут проходить через
несколько фигур сразу), для которых нужно добиться математического
условия (сейчас: сумма = цель). Игрок должен покрутить фигуры так, чтобы
ВСЕ линии одновременно выполняли своё условие — это и есть решение уровня.

Будет НЕСКОЛЬКО уровней (жёстко заданных заранее, не случайная генерация).
Ещё не решено: показывать все уровни на одном экране или отдельный экран
выбора уровня — решим на этапе фронтенда, на бэкенд-архитектуру не влияет
(в любом случае нужен список уровней + возможность выбрать/загрузить один).

Мультиплеер: любой подключённый игрок может крутить любую фигуру в любой
момент — совместное решение ОДНОЙ головоломки, все видят изменения в
реальном времени (через WebSocket, синхронизация состояния сервером).

Это НЕ приложение внутри Miro — отдельный самостоятельный веб-сервис.

## Архитектура (согласовано)
```
Браузер (клиент) <--WebSocket--> Python-сервер (FastAPI) <--WebSocket--> Браузер (клиент)
```
Сервер хранит состояние (текущие значения точек) как единый источник
правды. Клик по фигуре в браузере -> сообщение по WebSocket серверу ->
сервер поворачивает фигуру в PuzzleState -> рассылает всем подключённым
клиентам новое состояние -> все видят синхронно.

## Модель данных головоломки (реализовано и проверено)
Ключевая идея: точки существуют независимо от фигур. Фигуры и линии — это
просто СПИСКИ id точек, ссылающиеся на общий пул. Общие вершины между
фигурами получаются естественно: два Shape ссылаются на один и тот же
point_id.

- **Point** — id + value (число)
- **Shape** — id + point_ids (список ID точек ПО КРУГУ, порядок важен —
  именно он определяет направление и механику циклического сдвига)
- **Line** — id + point_ids + operation (пока только "sum") + target.
  Может ссылаться на точки из разных фигур одновременно.
- **Level** — неизменный шаблон: id, name, points, shapes, lines
- **PuzzleState** — состояние КОНКРЕТНОЙ игровой сессии (то, что реально
  меняется). Хранит level (шаблон) + values (dict point_id -> текущее
  значение, стартует из level.points, но дальше меняется независимо).
  Методы:
  - `rotate(shape_id, direction)` — direction: +1 или -1, ОДИН шаг за раз.
    Циклический сдвиг: `new_position = (i + direction) % n`.
  - `is_solved()` — True только если ВСЕ линии уровня одновременно
    выполняют условие.

Проверено на двух тестовых уровнях (см. "Структура проекта"):
1. Одна изолированная фигура (треугольник) — подтвердили, что поворот
   сохраняет сумму (естественно, для одной фигуры).
2. "Бабочка" — два треугольника с ОБЩЕЙ вершиной C, две диагональные линии
   через внешние точки (A-E и B-D). Подтвердили ключевой эффект: поворот
   одной фигуры меняет значение в общей точке, что затем влияет на
   следующий поворот СОСЕДНЕЙ фигуры — то есть фигуры реально связаны
   через общие вершины, как и задумано в головоломке.

## Структура проекта
```
Индивидуальное приложение/
├── .venv/                  (venv, в git не попадает)
├── .git/                   (репозиторий инициализирован и связан с GitHub)
├── app/
│   ├── main.py              (FastAPI-приложение, пока 1 маршрут GET "/")
│   ├── puzzle_models.py     (Pydantic-модели: Point, Shape, Line, Level)
│   ├── puzzle_engine.py     (PuzzleState: rotate(), is_solved())
│   └── static/
│       └── index.html       (ещё не создан)
├── run.py                   (запуск сервера: `python run.py`,
│                              uvicorn.run(..., host=127.0.0.1, port=8000,
│                              reload=True))
├── test_engine.py           (ручной тест: 1 треугольник, проверка что
│                              rotate/is_solved работают на простом случае)
├── test_engine_butterfly.py (ручной тест: 2 треугольника с общей вершиной,
│                              проверка связанности фигур через общую точку)
├── requirements.txt         (fastapi==0.115.0, uvicorn[standard]==0.32.0)
├── .gitignore                (.venv/, __pycache__/, *.pyc, .idea/, .obsidian/, *.log)
├── PROJECT_CONTEXT.md        (этот файл)
├── Занятие 1.md              (личная заметка пользователя, не код проекта)
└── .idea/, .obsidian/        (служебные, PyCharm и Obsidian, в git не попадают)
```

Путь к проекту на диске:
`D:\ДНД\Приложения_для_ДНД\Индивидуальное приложение`

Папка также используется как Obsidian-vault для личных заметок пользователя.

## Как запустить сервер локально
```
.venv\Scripts\activate.bat        (cmd)  ИЛИ  .\.venv\Scripts\Activate.ps1  (PowerShell)
python run.py
```
Сервер стартует на http://127.0.0.1:8000 — проверено, работает.

## Как запустить ручные тесты движка головоломки
```
python test_engine.py
python test_engine_butterfly.py
```
Оба сразу печатают результат в консоль, сервер для этого поднимать не
нужно — чистая проверка логики puzzle_engine.py.

## Swagger UI (встроенная документация FastAPI)
- **http://127.0.0.1:8000/docs** — Swagger UI, интерактивное тестирование
  HTTP-маршрутов прямо в браузере.
- **http://127.0.0.1:8000/redoc** — ReDoc, альтернативный вид документации.
ВАЖНО: WebSocket-эндпоинты в Swagger UI НЕ отображаются и не тестируются.

ЗАМЕЧАНИЕ: на компьютере пользователя есть также старый отдельный проект
`fastAPI_1`, у него был маршрут POST /register — если он тоже запущен и
слушает порт 8000, будет конфликт портов с текущим сервером.

## Известные технические нюансы (держим в памяти)
- Системный `python`/`py` не работают напрямую — обходим, вызывая venv
  напрямую или указывая полный путь к интерпретатору при создании venv.
- В PowerShell нужно активировать venv отдельной командой
  (`.\.venv\Scripts\Activate.ps1`) — активация в cmd не переносится в
  другое окно терминала.
- Пользователь иногда печатает текст не в той раскладке клавиатуры
  (кириллица/латиница) — если сообщение выглядит как бессмысленный набор
  русских букв, стоит попробовать декодировать его как английский текст,
  набранный в раскладке ЙЦУКЕН (например, "знсрфкь" = "pycharm").
