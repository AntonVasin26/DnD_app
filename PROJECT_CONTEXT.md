# Контекст проекта: Вращающаяся математическая головоломка (мультиплеер)

## Цель проекта (уточнено)
Это НЕ просто "клик -> поворот фигуры". Реальная концепция:

Головоломка из нескольких равносторонних многогранников (треугольники,
квадраты и т.д.). У соседних фигур есть ОБЩИЕ вершины (точки). В вершинах
стоят числа. При клике фигура поворачивается на 1 шаг по кругу (в любую
сторону), и числа в её вершинах циклически сдвигаются — включая общие
вершины с соседними фигурами, что связывает фигуры между собой.

Есть "линии" — произвольные наборы точек (могут проходить через
несколько фигур сразу), для которых нужно добиться математического
условия (сейчас: сумма = цель). Игрок должен покрутить фигуры так, чтобы
ВСЕ линии одновременно выполняли своё условие — это и есть решение уровня.

Будет НЕСКОЛЬКО уровней (жёстко заданных заранее, не случайная генерация).
Ещё не решено: показывать все уровни на одном экране или отдельный экран
выбора уровня — решим на этапе фронтенда, на бэкенд-архитектуру не влияет.

Мультиплеер: любой подключённый игрок может крутить любую фигуру в любой
момент — совместное решение ОДНОЙ головоломки, все видят изменения в
реальном времени (через WebSocket, синхронизация состояния сервером).

Это НЕ приложение внутри Miro — отдельный самостоятельный веб-сервис.

## Архитектура (согласовано)
```
Браузер (клиент) <--WebSocket--> Python-сервер (FastAPI) <--WebSocket--> Браузер (клиент)
```
Сервер хранит состояние (текущие значения точек) как единый источник
правды. Клик по фигуре в браузере -> сообщение по WebSocket серверу ->
сервер поворачивает фигуру в PuzzleState -> рассылает всем подключённым
клиентам новое состояние -> все видят синхронно.

ТЕКУЩИЙ СТАТУС: прототип интерфейса (app/static/index.html) пока работает
ПОЛНОСТЬЮ АВТОНОМНО на чистом JS, без связи с бэкендом (дублирует логику
rotate/сумм на клиенте вручную). WebSocket-подключение к реальному
PuzzleState с бэкенда — ещё предстоит сделать (см. план).

## Модель данных головоломки (бэкенд, реализовано и проверено)
Ключевая идея: точки существуют независимо от фигур. Фигуры и линии — это
просто СПИСКИ id точек, ссылающиеся на общий пул. Общие вершины между
фигурами получаются естественно: два Shape ссылаются на один и тот же
point_id.

- **Point** — id + value (число)
- **Shape** — id + point_ids (список ID точек ПО КРУГУ, порядок важен —
  именно он определяет направление и механику циклического сдвига)
- **Line** — id + point_ids + operation (пока только "sum") + target.
  Может ссылаться на точки из разных фигур одновременно.
- **Level** — неизменный шаблон: id, name, points, shapes, lines
- **PuzzleState** — состояние КОНКРЕТНОЙ игровой сессии. Методы:
  - `rotate(shape_id, direction)` — direction: +1 или -1, ОДИН шаг за раз.
    Циклический сдвиг: `new_position = (i + direction) % n`.
  - `is_solved()` — True только если ВСЕ линии уровня одновременно
    выполняют условие.

Проверено на бэкенде (test_engine.py, test_engine_butterfly.py) на
уровне "бабочка": два треугольника с общей вершиной C, диагонали
изначально были 2-точечные (A-E, B-D, target=6), позже во ФРОНТЕНД-
прототипе усложнили до 3-точечных диагоналей (A-C-E, B-C-D, target=9),
т.к. C геометрически лежит на пересечении обеих диагоналей. ВАЖНО: эта
логика 3-точечных линий пока реализована ТОЛЬКО в JS на фронтенде —
backend test-файлы (test_engine_butterfly.py) ещё используют старую
2-точечную версию, не синхронизированы. Нужно будет решить, приводить ли
их в соответствие при подключении реального WebSocket.

## Фронтенд-прототип (app/static/index.html) — реализовано
Полностью автономная (без сервера) HTML/CSS/JS-страница, дублирующая
логику puzzle_engine.py на клиенте для визуальной проверки идеи:

- SVG-отрисовка "бабочки": два равносторонних треугольника (сторона 200,
  высота стороны = side*sqrt(3)/2), расположены ГОРИЗОНТАЛЬНО (лежат на
  боку) — левый треугольник вершиной вправо, правый вершиной влево,
  общая вершина C посередине.
  Точки: A(120,150) верх-лево, D(120,330) низ-лево — база левого
  треугольника; B(432,150) верх-право, E(432,330) низ-право — база
  правого; C(276,240) общая вершина в центре.
- Клик по треугольнику (invisible `<polygon>` overlay поверх фигуры) ->
  JS-функция rotateShape(shapeId, direction) -> циклический сдвиг чисел
  у вершин этой фигуры (та же формула, что в puzzle_engine.py, только на
  JS: `((i + direction) % n + n) % n` — двойной `% n` нужен, т.к. в JS,
  в отличие от Python, остаток от деления отрицательного числа
  ОТРИЦАТЕЛЬНЫЙ, а не положительный).
- Таблички "Цель / Сумма" сбоку (справа), с короткими пунктирными
  соединительными линиями от точек E и B. Текст суммы красится в зелёный
  (класс sum-ok) если совпадает с целью, иначе тёмный (sum-wrong) — через
  JS classList.add/remove в функции render().
- render() вызывается один раз при загрузке страницы (в конце <script>),
  чтобы сразу синхронизировать текст с реальным состоянием values.
- Стартовые значения: A=1,B=2,C=3,D=4,E=5. Обе диагонали (A+C+E и B+C+D)
  изначально равны 9 (target=9 у обеих).

### Текстуры фона
Папка `app/static/textures/` (создана пользователем, перемещена из корня
проекта в app/static/, чтобы FastAPI мог её отдавать). Файлы:
  - floor.webp — плиточный паттерн, НЕ идеально бесшовный (замечен явный
    белый зазор при повторении, вероятно т.к. похоже на превью со стока
    маленького размера 389x262, не спроектирован как seamless tile)
  - background.jpg — тестировался, не использован в финальной версии
  - Tiles_Roughness.jpg — судя по названию, потенциально карта
    шероховатости из PBR-материала (не обязательно чисто цветная
    текстура), сейчас используется как фон блока #texture-test с
    background-repeat + background-size: 512px 512px. Пользователь
    сжал файл с 7.7 МБ до ~484 КБ перед использованием.
  Обсуждали (не сделано): извлечение бесшовных текстур пола из паков
  Dungeondraft (.dungeondraft_pack — на самом деле zip-архив с PNG).
  ВАЖНО: у таких паков обычно лицензия "личное некоммерческое
  использование" — стоит свериться с конкретной лицензией пользователя,
  если планируется публичный/коммерческий релиз приложения.

  ВАЖНЫЙ УРОК (баг, который решили): текстуры физически лежали в
  static/textures/, но браузер не мог их загрузить (404) — в main.py не
  было маршрута, отдающего произвольные файлы из static/, только сама
  index.html через FileResponse. Исправлено добавлением
  `app.mount("/", StaticFiles(directory="app/static"), name="static")`
  В КОНЦЕ main.py (после всех @app.get(...) — порядок важен, mount
  добавляется последним, иначе перехватит все маршруты raньше explicit
  routes).

  Текущий размер игровой области с текстурой: 853×480px (пропорция 16:9,
  как 1920×1080 уменьшенное в 1.5 раза; на момент финальной правки
  пользователь ещё раз попросил уменьшить в 1.5 раза с 1280×720, что и
  дало 853×480 — это и есть текущий финальный размер).

## Как запустить сервер локально
```
.venv\Scripts\activate.bat        (cmd)  ИЛИ  .\.venv\Scripts\Activate.ps1  (PowerShell)
python run.py
```

Открой http://127.0.0.1:8000 в браузере, чтобы увидеть прототип
головоломки с текстурой фона.

## Известные технические нюансы (держим в памяти)
- Системный `python`/`py` не работают напрямую — обходим, вызывая venv
  напрямую или указывая полный путь к интерпретатору при создании venv.
- В PowerShell нужно активировать venv отдельной командой
  (`.\.venv\Scripts\Activate.ps1`) — активация в cmd не переносится.
- Пользователь иногда печатает текст не в той раскладке клавиатуры —
  если сообщение выглядит как бессмысленный набор русских букв, стоит
  попробовать декодировать его как английский текст в раскладке ЙЦУКЕН
  (например, "знсрфкь" = "pycharm").
- Файлы, которые пользователь добавляет вручную через проводник (текстуры
  и т.п.), часто приходят с пробелами/кириллицей в имени — переименовываем
  в латиницу без пробелов перед использованием в коде (избегаем проблем
  с URL-путями).
- FastAPI НЕ раздаёт файлы из static/ автоматически — нужен явный
  `app.mount(...)` со `StaticFiles`, иначе будет 404 на любые ресурсы
  (картинки, css, js), кроме тех, что отданы через отдельный @app.get.
